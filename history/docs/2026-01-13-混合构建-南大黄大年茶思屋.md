# 混合构建方案分析

C2Rust采用逐函数转译+自动化测试验证的方式不断迭代，保证转译后的代码质量. 为了保证每次迭代都可以编译运行测试程序，必须实现Rust和C代码的混合构建.

C代码工程需要提供生成运行测试代码的命令，将Rust代码看成是独立的C文件生成的静态库或者动态库加入到原有的C构建工程是合理的方案，不会改变C构建工程的构建结果. 

实际场景中，C语言构建工程本身复杂多样, 除`CMake`以及`gnu autotool`比较常见的构建方案，还有部分开源软件提供构建脚本的自动生成工具, `bazel`等分布式构建方案, 在各种场景下如何自动将新增Rust生成的静态库或者动态库链接到最终构建结果中是提升C2Rust工具效率的一个关键技术点.

**说明**: `bazel`等分布式构建工具，当前常用策略都是单个C/C++文件的编译过程可能被分发到多个机器并发执行，但最终生成动态库或可执行程序的链接过程会在本地执行. 只关注链接过程，和其他本地构建方案没有本质区别.

## Rust构建库类别

Rust代码一定是构建为一个库，生成静态库还是动态库各有利弊. 

### 静态库方案.

Rust代码生成静态库，它的行为类似对应C函数独立为单独的C文件, 对于原构建结果，特别是测试程序的运行环境毫无影响. 但也有一些弊端.

Rust作为静态库添加到C工程的动态库和可执行程序的链接过程中，必须保证和原来C的构建过程相比不能引入多余的符号, 否则就可能导致后续的构建或者运行过程中因为符号冲突出现各种问题.

因为C代码是按编译单元作为链接的，一个编译单元对应一个C源文件，如果一个C源文件和一个Rust工程一一对应，也就是C代码的编译单元和一个Rust静态库一一对应，仅在需要C编译单元的地方链接对应的Rust静态库，可以保证不会引入多余的符号. 但是C的源文件之间的函数可能相互依赖, 最终要求多个Rust工程相互依赖, 这是无法支持的. 因此只能退而求其次, C代码的一个构建结果(静态库或者动态库或者可执行程序)和一个Rust工程一一对应.

C代码的一个构建结果和Rust工程一一会产生下面的要求:

1. 需要分析出C函数和C构建结果的映射关系. 这可以通过查看C构建结果包含的全局符号清单来实现.
1. 需要将Rust静态库准确链接到对应的C构建结果. 一旦错误链接，会出现包含多余符号的问题.
1. 需要支持同一个C函数被链接到多个C构建结果的场景. 这在C的构建工程中也不少见，多个C文件的不同组合生成不同的库是可能的.

此外，Rust静态库包含Rust ABI相关的符号，不能简单的去除，构建后的二进制大小较大，但这不影响C2Rust的测试验证功能。

### 动态库方案.

Rust代码生成动态库, 如果原来C代码生成静态库，可能会改变原来C构建结果之间的依赖关系. 比如下面的关系:

```shell
# ar rcs libfoo.a
# gcc -shared -o libbar.so libfoo.a -fPIC
# gcc -shared -o libbaz.so libfoo.a -fPIC
```

`libbar.so`和`libbaz.so`都依赖`libfoo.a`中的函数, 如果这个函数涉及全局变量的状态管理，那么原本`libbar.so`和`libbaz.so`之间行为相互解耦, 会因为多出的rust动态库最终耦合在一起.

实际应用中，几乎没有那个应用库限定只能使用静态库，因此虽然存在转译前后的潜在依赖关系不一致性的行为，但是都不会破坏程序的运行状态, 属于可以接受的范围.

相比静态库, 优势很明显:

1. 和C构建结果无对应关系，可以将多个C动态库或可执行程序包含的C函数打包到一个动态库中.
1. 无需准确对应C构建结果，即可以简单的为所有C构建的动态库和可执行程序链接Rust动态库，而不影响功能.

也有劣势:

1. 可执行程序运行时需要设置合适的环境，保证Rust动态库可以被定为. 这可以通过修改环境变量来实现.

### 结论

综合以上分析，Rust代码构建为动态库的方案更为简单可行, 相对最优.

动态库链接对于运行环境也是有影响的，需要保证执行测试程序的时候可以找到Rust动态库，也有两个方案:

1. 链接的时候通过rpath指定绝对路径: `-Wl,rpath=Rust动态库所在的绝对路径`, 不同链接器参数可能有差异.
2. 运行是通过环境变量指定: `LD_LIBRARY_PATH=Rust动态库所在的绝对路径` make test. 此方案相对通用.
3. 绝对路径链接动态库.

### 方案二: 劫持链接器

劫持链接器有两个方案:


#### 修改PATH环境变量.

好处是相对通用, 这在WINDOWS, LINUX上都支持. 但是从前面`CMake`的例子可以看出, 经过`cmake`处理后的构建脚本中的连接器已经是绝对路径，就需要分析各种工具获取链接路径的时候实现劫持, 对于交叉编译工具链，可能是通过相对路径去获取的. 也存在通过集中的配置脚本去获取. 这个方案实施起来相对困难.


#### 利用`LD_PRELOAD`. 

仅适用于Linux. 可以为当前shell下执行的每个可执行程序注入一个动态库，在这个动态库内部获取命令行参数，根据命令行参数判断是否需要添加Rust的动态库.

当需要添加Rust的动态库的时候，动态添加Rust动态库链接参数, 重启进程. 实现逻辑大致如下:

```c
__attribute__((constructor)) static void add_rust_dyn_lib(int argc, char* argv[]) {
	IF 判断如果不是生成动态库和可执行程序 或者 命令行参数已经包含了Rust动态库 THEN 
		返回
	ENDIF

        char* new_argv[argc + 2];
        for (int i = 0; i < argc; ++i) {
                new_argv[i] = argv[i];
        }
        new_argv[argc] = RUST动态库的链接参数.
	new_argv[argc + 1] = 0;
        execvp(argv[0], new_argv);
}
```

RUST动态库本身可以作为环境变量传入.

#### 总结

综合判断，选择`LD_PRELOAD`方案实现, 同时:

1. 链接程序为`ld`或`lld`
2. 绝对路径链接动态库.

## Example

本工程目录下的cJSON和rJSON是一个例子.

`cJSON/cJSON.c`文件的内容已经全部被注释掉，其原有内容已经全部用Rust重写，对应到`rJSON/src/lib.rs`中的实现.

整体构建过程如下:

```shell
$ cd xbuild
$ make # 生产libxbuild.so，支持混合构建.
$ cd rJSON
$ cargo buid #正常rust动态库
$ cd ../cJSON
$ mkdir build #准备cmake构建目录
$ cd build
$ cmake .. #生成cmake构建脚本
$ LD_PRELOAD=`pwd`/../../libxbuild.so XBUILD_RUST_LIB=`pwd`/../../rJSON/target/debug/librjson.so make #实现混合构建.
$ make test #运行测试
```
