**数据类型映射：**
- C 的基本数据类型 -> c_<type>, 比如int -> c_int.
- C 的非基本数据类型，完全映射为同名的Rust类型.
- C 函数指针类型 → Rust `Option<fn()>`包装的函数指针。

**常量处理:**
- C语言的字符常量应该转换为rust的u8类型,比如`'c'` -> `b'c'`
- C语言的字符串常量应该转为Rust的`[u8]`类型常量，且增加NULL结束符,比如`"hello"` -> `b"hello\0"`
- 如果C字符串常量是空字符串 `""`，翻译结果必须是 `b"\0"`，绝对不能生成 `b""\0"` 这类非法Rust字节串

- 如果使用 Rust 的 C 字符串字面量形式 `c"..."`，必须直接使用 `c"...".as_ptr()`。
- Rust 的 `c"..."` 字面量本身会自动包含结尾的 NUL，绝对禁止在 `c"..."` 内再手写 `\0`。
- 绝对禁止把 `c"...".as_ptr()` 再包装成 `&... as *const [...]`、`.as_ptr().as_ptr()`、slice/raw-slice 指针等额外层级。
- 泛化示例：
  - 正确：`c"\r%80s\r".as_ptr()`
  - 正确：`c"".as_ptr()`
  - 正确：`c"some_function".as_ptr()`
  - 错误：`c"\r%80s\r\0".as_ptr()`
  - 错误：`c"%u, \0".as_ptr()`
  - 错误：`c"some_function".as_ptr().as_ptr()`
  - 错误：`b"some_function\0".as_ptr() as *const ::core::ffi::c_char.as_ptr()`

**命名处理：**

**函数内静态变量处理：**

**指针处理：**
- Rust中需要通过 `&raw const` 或 `&raw mut`的形式获取原始指针。
- 对于静态数组、全局数组、`static mut` 数组：

  - 不要为了取首元素指针而生成会依赖不稳定特性的写法；
  - 不要把“数组长度”翻译成 `size_of::<某个臆造元素类型>()` 这类表达式；

  - 泛化示例：
    - C: `static mut BUF: [u8; 136]` + `fill(BUF, sizeof(BUF))`
    - 正确思路：传递首元素裸指针，并使用编译期长度 `136`
    - 错误思路：`BUF.len()`、`size_of::<BUF_element>()`、对 `BUF` 形成共享引用
  - 必须识别下面这些“看起来在算长度、但本质仍在借用 static mut”的错误写法，并避免生成：

    - `fill(addr_of_mut!(BUF).cast(), core::mem::size_of_val(&BUF))`
    - `fill(addr_of_mut!(BUF).cast(), core::mem::size_of::<[u8; BUF.len()]>())`
  - 对同一类场景，目标写法应直接落成编译期常量，例如：
    - `fill(::core::ptr::addr_of_mut!(BUF).cast(), 136usize)`
  - 如果数组声明本身已经是 `[T; N]`，那么 `sizeof(BUF)` 的 Rust 对应值就是编译期常量 `N * size_of::<T>()`；不要再从 `BUF` 的值出发推导长度。
- 如果C代码中某处的C指针数据没有进行非空判断就执行了解引用操作，那么翻译结果可以将它翻译为一个引用类型。

- 只有当“当前调用点”要求裸函数指针时，才允许对 `Option<fn>` 调用 `.unwrap()`。
- 如果被调用函数签名本身要求 `Option<fn>`，必须直接传递 `Option<fn>`，绝对不要多余地 `.unwrap()`。
- 如果某个 FFI 函数参数要求 `*mut c_void` / `*const c_void`，必须显式把具体类型指针转换成对应的 `c_void` 指针，不能直接把 `*mut i8` / `*mut T` 原样传入。
